# Stage C — Single Schema Authority (P1-02 / P2-01)

**Branch:** `arena/d78ebf88-gerege-ai-agent` · **Base:** `7676442` (Stage B closed)
**Scope:** audit findings **P1-02** (two competing schema definitions) and **P2-01**
(drift checker structurally blind to type changes).
**Verdict:** both findings **CLOSED**, with the root cause removed rather than patched.

---

## 1. What was wrong

There were **three** independent definitions of the same database:

| Source | Owner | Shape |
|---|---|---|
| `core/models.py` | Alembic target metadata | `DateTime`, typed `String(n)` |
| `migrations/versions/0001_*.py` | Alembic | `String(64)` timestamps, `CAST(CURRENT_TIMESTAMP AS VARCHAR)` |
| `database.init_db()` | runtime DDL (~350 lines) | `TIMESTAMP` + untyped `TEXT` for every string |

Measured against a database built from `core/models.py` (the reference):

| Starting schema | Diffs vs models |
|---|---|
| `create_all(models)` | **0** |
| Alembic `0001` | **58** |
| legacy `init_db()` runtime DDL | **112** |

So the schema depended on *how* a database happened to be created. Two of the
differences were not cosmetic — they broke inserts outright:

* `registrations.service` was `NOT NULL` in `0001` but the ORM never sets it, so every
  registration created through the app failed on a strict schema.
* `invoices.description` had the same problem.

And `verify_schema_drift()` could not see any of it: it AST-parsed two *source files*
and compared column **names**, never types, never the live database. It was dead code
that nothing called.

## 2. What changed

### New single authority
* `core/schema_manager.py` — `ensure_schema()`, `current_revision()`, `is_at_head()`,
  `compare_with_models()`, `drift_report()`, `preflight()`. PostgreSQL upgrades take a
  session advisory lock (`6477728151042314001`) so concurrent worker boots cannot race;
  the revision is re-read after acquiring the lock, and the post-condition is asserted.
* `database.init_db()` no longer contains a single `CREATE TABLE`. It calls
  `ensure_schema()` and then does **data only**: default tenant row, magic token, legacy
  `page_id` cleanup. 388 lines removed, and with them the bare `except: pass` block.

### Migration `0002_schema_authority`
Hand-written (the autogenerated candidate was rejected — see §6). It converges **all
three** starting shapes onto the models:

| Starting schema | After 0002 |
|---|---|
| `create_all(models)` | 0 diffs |
| `0001` | 0 diffs |
| legacy `init_db()` DDL (PostgreSQL) | 0 diffs |
| legacy `init_db()` DDL (SQLite) | 0 diffs |
| **partial** legacy DB (3 of 17 tables, fewer columns) | 0 diffs |

It is defensive on every step: table/column/index/constraint existence is inspected
before acting, so it is safe on partial and already-correct schemas alike.

### `migrations/env.py` — the actual P2-01 fix
`compare_type=True` and `compare_server_default=True` were added, plus
`render_as_batch` for SQLite. Without `compare_type`, autogenerate only compared names,
which is precisely why the drift was invisible.

### `verify_schema_drift()` — no longer blind
`core/db_engine.py` now delegates to `core.schema_manager.drift_report()`, comparing the
**live database** with the models through Alembic's autogenerate machinery.

Proof it works (same database, `0001` only):

```
has_drift = True | diff_count = 58
by_kind = {'modify_type': 34, 'add_index': 11, 'modify_nullable': 3,
           'remove_index': 8, 'remove_constraint': 1, 'add_constraint': 1}
```

The old checker reported **no drift** for this database.

## 3. Three real bugs found while testing (not in the original audit)

Testing the migration against real data surfaced defects that reading the code would
not have:

### 3a. SQLite batch mode silently destroys every timestamp — **critical**
Alembic's batch rebuild copies rows with `CAST(col AS DATETIME)`. SQLite resolves that
cast with **NUMERIC affinity**, so a timestamp string silently becomes its leading
integer. No error, row counts unchanged, data gone:

```
BEFORE  id=1 '2026-11-16 04:05:06' (text)      id=2 '' (text)
AFTER   id=1  2026                  (integer)  id=2  0  (integer)
```

Fix: `migrations/sqlite_compat.py` replaces the cast with SQLite's `datetime()`, which
normalises the format, maps `''` → `NULL`, and keeps the value as TEXT. Offset by
`tests/test_stage_c_schema.py::test_sqlite_batch_migration_does_not_truncate_timestamps_to_integers`
and the `typeof()` assertion in `scripts/verify_migration_0002.py`.

### 3b. `init_db()` seeded the wrong database — split-brain
`get_connection()` passed `sqlite_path=DB_PATH` explicitly, which meant
`get_sqlite_db_path()` **never read the `DB_PATH` environment variable**. An operator who
set it still had `init_db()` seed the repository-local `leads.db` while the app read
their configured file. Fix: resolution now honours `DB_PATH` while keeping the
`database.DB_PATH` override that tests and tooling rely on.

The same class of bug existed between `ensure_schema()` (env-resolved) and
`get_connection()` (module-global-resolved); both now go through one resolver,
`core/schema_manager._resolved_sqlite_path()`.

### 3c. `created_at` became NULL for raw inserts
The legacy DDL had `DEFAULT CURRENT_TIMESTAMP`; the models only had a Python-side
`default=datetime.utcnow`, which does not apply to raw SQL. Dozens of `database.py`
helpers insert by raw SQL, so their rows got `NULL` timestamps. Fix: `TS_DEFAULT`
(`func.current_timestamp()`) added to the 18 timestamp columns in `core/models.py`;
`0002` re-establishes the database-side default after the type change.

## 6. Rejected: the autogenerated migration

`alembic revision --autogenerate` produced `074826f6cb71` (401 lines). Rejected because:

1. `op.alter_column` emits **no `USING` cast** for `VARCHAR(64) → timestamp`, so PostgreSQL
   errors on any non-empty `created_at`. Since every production row has one, the
   autogenerated migration cannot run on a real database at all.
2. It generated `existing_server_default=sa.text('(CURRENT_TIMESTAMP)::character varying')`,
   which is PostgreSQL-dialect-specific and wrong for SQLite.
3. It could not handle the "drop the default before retyping" ordering that PostgreSQL
   requires (found by running it: `DatatypeMismatch`).
4. It produced no real `downgrade()`.

The hand-written revision uses explicit `postgresql_using=` casts, drops defaults
first, backfills before tightening constraints, and has a working inverse — verified by
the three-step round trip above.

## 7. Operational notes

* `python scripts/migrate.py --check` — pending revisions, no writes.
* `python scripts/migrate.py --dry-run` — print the SQL.
* `python scripts/migrate.py` — **takes a backup first**, applies, verifies, then asserts
  the database is at head. Exit codes: 0 ok, 1 failure, 2 not-at-head.
* `python scripts/migrate.py --verify` — type-aware drift assertion (used in CI).
* Serverless: `vercel.json` now declares `includeFiles: ["migrations/**", "alembic.ini"]`
  and `ensure_schema()` raises a descriptive error naming the missing paths if a bundle
  omits them, instead of an opaque Alembic traceback.

### Known limitation (documented, not hidden)
`compare_server_default` is **off** in the default drift gate. `0001` attached 62 literal
defaults (`status DEFAULT 'Шинэ'`, `channel DEFAULT 'web'`, …) that the models express as
Python-side `default=`; every insert path passes those columns explicitly. Chasing them
would mean 62 cosmetic `SET DEFAULT` statements for no behavioural gain. It is available
as an opt-in audit via `compare_with_models(include_server_defaults=True)`.

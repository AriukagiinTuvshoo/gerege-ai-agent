  cap = 10000
  victim count = 19 of 20 (window LIVE)

  victim count after pressure = 0
  victim's next attempt -> allowed=True count=1

  EXPECTED: victim still at 19/20, next attempt the 20th
  ACTUAL  : budget erased, next attempt started a fresh window at count=1
  RESULT  : LIVE-BUDGET EVICTION REPRODUCED

## 3. Root causes at this commit
   _MemoryCounter.window_seconds is mutated by max(...) on every admission, so a later
   admission redefines an existing generation's lifetime. Redis writes the TTL once, in
   the script that creates the counter, and never revisits it.
   AdmissionToken.window_seconds carries the caller's requested window, not the
   generation's actual window, and _MemoryStore.refund_admission judges expiry by it.
   _MemoryStore._evict_if_needed() reclaims expired entries and then drops the oldest
   LIVE counter when still over cap, despite its docstring claiming the opposite.
